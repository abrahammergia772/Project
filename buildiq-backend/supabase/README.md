# Supabase schema & policies

SQL for the BuildIQ Postgres database.

```
supabase/
├── migrations/
│   ├── 0001_schema.sql            Tables, constraints, indexes
│   ├── 0002_rls_policies.sql      Row Level Security — deny-by-default
│   └── 0003_rls_supabase_auth.sql Optional: per-role RLS (not applied)
├── seed.sql                       The nine departments
└── README.md
```

---

## Applying

**With psql** (works anywhere):

```bash
export DATABASE_URL="postgresql://postgres.<ref>:<pw>@aws-0-<region>.pooler.supabase.com:6543/postgres"

psql "$DATABASE_URL" -f supabase/migrations/0001_schema.sql
psql "$DATABASE_URL" -f supabase/migrations/0002_rls_policies.sql
psql "$DATABASE_URL" -f supabase/seed.sql        # optional
```

> Note the URI scheme. The API uses `postgresql+psycopg://` (SQLAlchemy needs
> the driver name); `psql` wants plain `postgresql://`.

**With the Supabase CLI:**

```bash
supabase link --project-ref <your-ref>
supabase db push
```

**Or skip it entirely.** The API calls `create_all()` on boot and will build
the tables itself. You get the same tables, but not the CHECK constraints or
partial indexes defined here — those are additions this schema makes over what
the ORM declares.

## Why RLS is deny-by-default

The API is the only client of this database, and it connects as `service_role`,
which **bypasses RLS**. Authorization for real traffic lives in Python
(`app/security.py`, `app/deps.py`), where every query is scoped by role.

RLS still matters because the **anon key is public** — it ships in browser
JavaScript. Without RLS, anyone with that key could read every row through
Supabase's auto-generated PostgREST API, going straight around the backend.

So `0002` enables RLS on all 15 tables, revokes the default grants, and adds
restrictive deny-all policies for `anon` and `authenticated`:

| Client | Access |
|---|---|
| The API (`service_role`) | Full — unaffected by RLS |
| Anon key / PostgREST / supabase-js | **Zero rows, every table** |

Credential material gets a second layer that doesn't depend on RLS at all:
`password_reset_tokens` is revoked outright, and `SELECT` on
`users.hashed_password` is revoked at column level.

Storage follows the same shape: the `buildiq-documents` bucket is forced
private, and downloads are streamed through `GET /documents/{id}/download` so
role checks apply to files too.

### If you later query Supabase from the browser

`0003_rls_supabase_auth.sql` reproduces the entire role model as SQL policies —
project scoping per role, Workforce-only attendance writes, auditors excluded
from complaints, per-user notification targeting.

It is **written but deliberately not applied**; the file raises an exception if
you run it. It assumes Supabase Auth with `public.users.id = auth.uid()`, which
isn't true today since the backend issues its own JWTs and ids. Read it, migrate
identities, then remove the guard block.

## What the schema adds over `create_all()`

Both produce the same tables. This SQL additionally enforces:

**CHECK constraints** — valid roles, statuses and enums at the database level:

```sql
constraint ck_users_role check (role in ('Super Admin','General Manager',
    'Department Manager','Project Manager','Engineer','Auditor','Client'))
constraint ck_projects_progress check (progress between 0 and 100)
constraint ck_audit_anomaly_score check (anomaly_score between 0 and 1)
```

**The attendance invariant** — a Present day can never carry an absence reason:

```sql
constraint ck_attendance_reason_only_when_absent check (
    status = 'Absent' or reason is null)
```

That mirrors the API's own rule and is what the flaky test we fixed earlier was
actually tripping over. Enforcing it here means it holds no matter what writes
to the table.

**Partial and GIN indexes** for the hot paths:

```sql
-- Anomalies tab reads flagged rows worst-first
create index ix_audit_logs_flagged_score on audit_logs (anomaly_score desc)
    where is_flagged;

-- Notification targeting is a JSONB containment test
create index ix_notifications_target_roles on notifications using gin (target_roles);

-- Multi-role membership: roles ? 'Project Manager'
create index ix_users_roles_gin on users using gin (roles);
```

## Seeding

`seed.sql` inserts only the nine departments.

The full demo dataset — 46 users with bcrypt-hashed passwords, 15 projects,
30 days of attendance, AI-classified complaints, 84 audit log entries — is
generated by `app/seed.py` on first boot, because it needs password hashing and
the complaint classifier. Set `SEED_ON_STARTUP=true`.

For a clean production database: run `seed.sql`, set `SEED_ON_STARTUP=false`,
and create the first admin through `POST /auth/signup` (note that self-service
signup refuses privileged roles, so promote the account with a direct SQL
update, or seed it deliberately).

## Verifying

```sql
-- RLS on everywhere? Expect 15 rows, all true.
select tablename, rowsecurity, forcerowsecurity
from pg_tables where schemaname = 'public' order by tablename;

-- Which policies exist?
select tablename, policyname, permissive, roles
from pg_policies where schemaname = 'public' order by tablename;
```

```bash
# The anon key must return nothing.
curl "$SUPABASE_URL/rest/v1/users?select=*" -H "apikey: $SUPABASE_ANON_KEY"

# The API must still work — it uses service_role.
curl http://localhost:8000/health
```

## Migrations

`0001` uses `create table if not exists`, so it's safe to re-run, but it won't
alter an existing table. Once you have production data, adopt Alembic:

```bash
pip install alembic
alembic init migrations
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
```

Then set `SEED_ON_STARTUP=false` and stop relying on `create_all()`.
